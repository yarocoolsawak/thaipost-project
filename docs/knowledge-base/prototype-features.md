บันทึกฟีเจอร์ที่เพิ่มใน prototype (branch `addon`) พร้อมเหตุผลและข้อมูลที่ต้องใช้ตอนทำจริง

> **ยังไม่ได้อัปเดตใน Demo guide และ Flow changelog:** รออัปเดตพร้อมกันทีเดียว

## ตรวจ CEC กับปลายทางจริง

*เพิ่ม 15 ต.ค. 2569*

**ปัญหาเดิม**
- เคสต้องรอสถานะพัสดุถึงศูนย์ปลายทางก่อนถึงจะรู้ CEC (สถานะ "รอระบุ CEC")
- แต่รหัสไปรษณีย์ผู้รับมีอยู่ในออเดอร์ตั้งแต่แรก จึงไม่จำเป็นต้องรอ
- ความเสี่ยงที่เหลือคือร้านค้าพิมพ์รหัสไปรษณีย์ผิด

**ทำงานอย่างไร**

1. **ตอนเปิดเคส:** ระบุ CEC จากรหัสไปรษณีย์ผู้รับทันที แล้วส่งเข้าคิว CEC
   - ถ้ารหัสไม่มีในตาราง เคสจะเป็น "เคสใหม่" พร้อมป้าย "ไม่พบ CEC ของรหัสไปรษณีย์" ให้ส่วนกลางเลือก CEC
   - เอาสถานะ "รอระบุ CEC" ออกแล้ว
2. **ทุกครั้งที่ QMS อัปเดตสถานะ:** เทียบที่ทำการที่พัสดุไปถึงจริงกับ CEC ของเคส
   - **CEC ไม่ตรงปลายทางจริง:** สถานะถึงที่ทำการปลายทาง (รหัส 3, 35, 301, 302) แต่ที่ทำการนั้นอยู่ใน CEC อื่น
   - **สาขาแจ้งผิดเขต / ที่อยู่ผิด:** สาขาแจ้ง 40 ผิดเขต, 20 จ่าหน้าไม่ชัดเจน, 21 ไม่มีเลขบ้าน หรือ 26 ย้าย / ไม่ทราบที่อยู่ใหม่
   - ไม่เช็คสถานะที่ศูนย์คัดแยกระหว่างทาง เพราะอยู่คนละจังหวัดอยู่แล้ว
   - ถ้าพัสดุไปถึงที่ทำการของ CEC เดิมในภายหลัง ป้ายเตือนจะหายเอง
3. **แจ้ง ปณ.ส่วนกลาง:**
   - เด้งแจ้งเตือนเมื่อดึงสถานะจาก QMS หรือรีเฟรชข้อมูลแล้วพบเคสใหม่ที่ไม่ตรง
   - มีแถบเตือนบนคิวงาน และเมนู "ปลายทางไม่ตรง CEC" พร้อมจำนวนในแถบด้านข้าง
   - แสดงป้ายใต้ CEC ในตารางทุกมุมมอง และปุ่ม "ตรวจ CEC" ในแถวของเคส
4. **ส่วนกลางตัดสินใจ:** ในหน้าเคสเลือกได้ 2 ทาง ทั้งสองทางบันทึกในประวัติเคส
   - **ย้ายไป CEC ใหม่:** ระบบเลือก CEC ของที่ทำการจริงไว้ให้แล้ว
   - **CEC เดิมถูกต้องแล้ว:** แจ้งเตือนเดิมจะไม่เด้งซ้ำ

**เคสตัวอย่างในเดโม:** `TP-2026-0025` / `EN100200321TH`
- ที่อยู่ผู้รับอยู่นครราชสีมา (30000) แต่ร้านพิมพ์รหัสเป็น 38000 (บึงกาฬ)
- เปิดมาจะเห็นเตือน "ผิดเขต" จาก ปณ.บึงกาฬ
- กด "ดึงสถานะจาก QMS" 2 ครั้ง พัสดุจะถึง ปณ.นครราชสีมา แล้วเตือน "CEC ไม่ตรงปลายทางจริง" พร้อมแนะนำ CEC ปข.3 (ตามไฟล์ที่นำเข้า 30 ต.ค.)

**ข้อมูลที่ต้องใช้ตอนทำจริง**

| ข้อมูล | สถานะ |
|---|---|
| รหัสไปรษณีย์ผู้รับ | มีในออเดอร์ MyOrder |
| ชื่อและรหัสไปรษณีย์ของที่ทำการในทุกสถานะ | Webhook EMS และ Drop-off ส่งมาอยู่แล้ว |
| **เอกสาร mapping รหัสไปรษณีย์ → ปณ.ปลายทาง → กลุ่ม CEC** | ได้รับ `PostOffice_68_07.xlsx` แล้ว 30 ต.ค. 2569: ใช้รหัสครบ 5 หลัก → ที่ทำการ → CEC; ยังต้องยืนยันความเป็นปัจจุบันและความครอบคลุมพื้นที่นำจ่าย |
| ความหมายรหัสสถานะ EMS ครบ (ยืนยันรหัสถึงปลายทางและรหัสผิดเขต) | ได้บางส่วน ต้องขอเอกสาร webhook EMS |

## ทะเบียนที่ทำการจากไฟล์ ปณท

*เชื่อม prototype 30 ต.ค. 2569*

**ต้นฉบับ:** [PostOffice_68_07.xlsx](sources/PostOffice_68_07.xlsx) เก็บโดยไม่แก้ไข · SHA-256 `4c8c81d8cfd5bbb8099232e693cb5574361cec2ab6c6a014014a191c1844f86a`

- ชีต `ปณ.`: B1 ชื่อเอกสาร, B2 “สถานะ วันที่ 31 ก.ค. 2568”, B3:F3 หัวตาราง, B4:F1203 ข้อมูล 1,200 แถว
- คอลัมน์: B ลำดับ, C สังกัด, D รหัสไปรษณีย์, E ที่ทำการไปรษณีย์, F ไลน์กลุ่ม CEC ปน./ปข.
- 1,200 รหัสไม่ซ้ำ เก็บเป็นข้อความ 5 หลัก · 14 กลุ่ม: CEC ปน.1–4 และ CEC ปข.1–10
- ไม่มีเบอร์โทร อีเมล LINE URL รายชื่อสมาชิก จังหวัด หรือกติกา SLA; ชื่อกลุ่ม LINE ไม่ใช่ URL ที่ใช้ส่งข้อความได้

**ใช้จริงใน prototype**
1. ปุ่ม “ที่ทำการ / CEC” บนแถบหัว: ค้นรหัส ชื่อ และสังกัด กรอง CEC แสดงครั้งละ 50 แถว ระบุวันข้อมูลและต้นฉบับ
2. ใช้รหัสตรง 5 หลักระบุสาขาและ CEC เมื่อเปิดเคส; ปรับ assignment ของเคสจำลองจากตารางเดียวกัน ชื่อในข้อความ/ประวัติจำลองเก่าบางรายการยังเป็นตัวอย่างเดิม
3. ไม่มี fallback จาก prefix สองหลัก จังหวัด หรือ CEC กลุ่มแรก; ไม่พบรหัสต้องให้ส่วนกลางตรวจ เลือก CEC และสาขาจากรายการ
4. ตรวจรหัสสาขาจริงใน QMS กับกลุ่มในตารางเดิม การย้ายกลุ่มต้องเลือกสาขาในกลุ่มนั้นด้วย และบันทึก audit
5. ชื่อ CEC บนคิวและตัวกรองใช้ชื่อจริง ปน./ปข.; จำนวนที่ทำการแยกจากจำนวนสมาชิก LINE; ไม่แสดงเบอร์โทร CEC จำลองเป็นเบอร์จริง
6. มุมมองสาขาแสดงเคสของสาขาที่เลือก ไม่ดึงเคสเกิน SLA ของสาขาอื่นเข้ามาปะปน

**ข้อจำกัด / งานต่อ (Q-02)**
- ไฟล์ระบุสถานะ 31 ก.ค. 2568 ต้องยืนยันการเปิด/ปิด/ย้ายสังกัดล่าสุดก่อนใช้ production
- รหัสในไฟล์เป็น key ของรายการที่ทำการ ไม่ใช่ตารางความครอบคลุมตำบลหรือข้อยืนยันว่าทุกรหัสผู้รับจับคู่สาขานำจ่ายได้โดยตรง ใช้ exact match สำหรับ demo; production ให้รหัสสาขาปลายทางจาก ปณท เป็นหลักและใช้รหัสผู้รับเป็นข้อมูลประกอบ

## การรอยืนยันและปิดเคสอัตโนมัติ (เพิ่มใน prototype 2 พ.ย. 2569)

- CS ตั้ง timeout ต่อประเภทได้ (default 72 ชม., 1–720 ชม.) เปิด/ปิดได้ แต่ NOT_RECEIVED บังคับปิด auto เสมอ
- เจ้าหน้าที่ส่งผลแก้ไขที่เผยแพร่ให้ร้านค้าแล้วจึงเริ่ม confirmation version และ deadline; โน้ตภายใน/ข้อความทั่วไป/ส่งคำตอบเดิมซ้ำไม่เริ่มเวลาใหม่
- ครบกำหนดเคสทั่วไปไม่ตอบ → CLOSED / Archived เหตุผล NO_RESPONSE_TIMEOUT; ไม่เติม acceptedBy/acceptedAt
- auto_sla ที่ยืนยันรอบ mock แล้ว ไม่มีเรื่องจากร้านค้า และสถานะปัจจุบัน delivered → DELIVERED_AUTO; manual/disputed ไม่ปิดตามสถานะนี้
- NOT_RECEIVED / deliveryDisputed ปิดได้ด้วยการยอมรับจาก role MERCHANT เท่านั้น; ครบ 72 ชม.สร้าง activity ติดตามให้ CS/สาขา
- ข้อความร้านค้า/แอดมิน, อีเมลคำร้อง หรือกดไม่จบ ยกเลิก timer และใช้เคสเดิมแม้ปิดแล้ว; ปุ่มเซ็นรับไม่ได้รับของตั้ง sticky flag ที่ไม่หายจากการเปลี่ยนประเภท
- แสดงแผง lifecycle ในหน้ารายละเอียดเคส; ตั้งเวลาได้ที่ header ฝั่ง CS; มุมมอง Archived ใช้ CLOSED
- ป้องกันซ้ำด้วย shop/order/tracking (demo หนึ่ง order หนึ่ง barcode); สร้าง auto_sla จาก mock order SHIPPED ที่มี event ถึงสาขาปลายทางตรงรหัสและเกิน 72 ชม. ไม่ใช้ fallback วันเปิดเคส
- เก็บเคสและการตั้งค่าใน localStorage ตรวจเวลาทุก 15 วินาทีขณะเปิดแอป และตรวจย้อนหลังเมื่อเปิดอีกครั้ง; งานหา auto_sla ตรวจตอนเปิดและทุกชั่วโมง
- **ข้อจำกัด prototype:** ไม่มี backend worker / push / email จริง การเตือนเป็น activity ในแอป; production ต้องใช้ shipment/cycle ref ที่ ปณท ยืนยัน, auth ฝั่ง server, scheduler, notification outbox และ transaction ก่อนปิดเคส
- ทดสอบ: `node --test scripts/case-lifecycle.test.mjs scripts/post-office-routing.test.mjs` (15 กรณี)
